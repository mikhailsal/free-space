# Small-folder refresh without keeping every small path

The practical 4 GiB pilot is a single comparison per case, not a production result. On the directory-heavy profile, the prototype stored two coarse database images in 32 KiB after 100,276 entries. Refreshing the retained 74-entry subtree visited 148 entries and took 0.0654 s; requesting an omitted 100-entry subtree selected the root, visited 200,552 entries over two passes and took 26.5757 s, versus 1.1678 s for v1 and 0.1658 s for v2 in that case ([pilot report](cleanup-threshold-initial-smoke-2026-11-02.md)). The omitted-target result is the central tradeoff, not an estimate for all workloads. The prototype deliberately discarded the old target contribution; `nearest` chooses a retained ancestor and refresh walks that boundary ([selection and update](https://github.com/mikhailsal/free-space/blob/678e998e47020576224337b8fe8ab941f3df2bef/cli/examples/cleanup_probe/main.rs#L105), [refresh](https://github.com/mikhailsal/free-space/blob/678e998e47020576224337b8fe8ab941f3df2bef/cli/examples/cleanup_probe/main.rs#L283)).

A current scan of a small folder tells us its **new** contents, not what that folder contributed to the old anonymous bucket. Two old trees can have identical parent totals and counts but assign different portions to that folder. Without an old contribution, trustworthy change record, or old filesystem snapshot, no algorithm can derive the exact old-to-new delta for that particular folder from the aggregate alone. Even knowing its old total does not always let us remove its old `min_scanned_at` or `newest_mtime`: if it supplied a bucket extremum, the runner-up is not in a simple aggregate. A fresh live view and an exact refreshed persisted snapshot are therefore separate products.

## 1. Live drill-down; keep coarse baseline until a wider refresh

**State:** Retain exactly the existing coarse anchors and anonymous buckets, with observation times and unknown/error indicators. On request, scan the requested live subtree into an ephemeral bounded result and show current named children and totals, without replacing the historical anonymous contribution. The selected subtree need not have existed as a retained node. Existing authenticated local API and server machinery can carry a new explicit operation, subject to access and resource limits ([server](https://github.com/mikhailsal/free-space/blob/678e998e47020576224337b8fe8ab941f3df2bef/cli/src/serve/mod.rs#L71), [API](https://github.com/mikhailsal/free-space/blob/678e998e47020576224337b8fe8ab941f3df2bef/cli/src/serve/api.rs#L138)).

**Cost:** No new persistent per-small-file or per-small-directory index; per-request work is proportional to the visited requested subtree and hardlink-accounting policy, with bounded in-memory/spill limits. This is a theoretical design, not an observed timing. A later exact persisted update still needs a retained-boundary/root scan or another source of the old value. Repeated requests repeat traversal. If the UI must show a new exact global total immediately, this option alone does not meet that contract.

**Correctness:** Clearly mark live results with their own observation time and distinguish them from old baseline totals; do not add a current subtree total to an old bucket or present a live rescan as historical diff. A subtree-only hardlink scan may not know the globally attributed owner, so return an explicitly qualified local view or consult reliable global link state. Unknown directories and cross-filesystem/mount behavior must be visible. Crossing the threshold can be shown in the live view, but it cannot change the old snapshot's retained structure without a proper update.

## 2. Capped aggregate frontier, with exact fallback

**State:** In addition to named anchors, retain a **strictly capped** set of routing/frontier directory records, selected by explicit policy such as recently requested/cleanup targets, important paths or aggregate size. A record contains raw path identity, parent/bucket association, old attributed allocated and apparent totals, entry counts, errors/unknown status, old minimum scan time and maximum clamped file mtime, generation/threshold and enough link-accounting information to make its old contribution meaningful. It stores no ordinary per-file names and does not retain every small directory. A frontier entry is directory identity and an aggregate, so this deliberately retains *some* small-directory identities, not zero. Reserve root and essential anchors first, then cap bytes as well as rows; evictions must be explicit.

**Update:** If the requested folder has a valid exact frontier record, rescan it and replace its old contribution with its new contribution in the appropriate ancestor/bucket. Publish updated totals and any promoted/demoted retained anchors as a coherent generation. On cache miss, eviction, untrusted old state, cross-boundary hardlink ambiguity or unsupported path/mount conditions, rescan the nearest boundary for which the old contribution and complete recomputation are known; this can still be the full root. Never invent a zero old contribution. The current example already has the safe fallback shape but no extra frontier ([prototype](https://github.com/mikhailsal/free-space/blob/678e998e47020576224337b8fe8ab941f3df2bef/cli/examples/cleanup_probe/main.rs#L283)).

**Cost and limits:** Persistent additional storage and memory for the frontier are bounded by the configured cap; actual bytes, indexes, path lengths and update cost must be measured. A hit scans the selected subtree plus propagation/transaction work, not necessarily only that subtree if extrema, link groups or promotion affect wider state. A fixed cap cannot ensure every arbitrary folder is cached: adversarial access or many small directories forces misses and the same worst-case wide rescan. Persisted ancestor exactness must also handle threshold crossings: rescan enough of the changed region to discover newly retained nodes, fold a demoted region correctly, and preserve one-count-only bucket accounting.

**Freshness and hardlinks:** To remove a previous minimum/maximum exactly, store a suitable bounded summary with multiplicities/runner-up information and a safe invalidation rule, or rescan the relevant containing bucket when that summary is insufficient. Unbounded distinct timestamp values cannot be promised away with a fixed-size exact summary for arbitrary updates. Cross-boundary hardlinks need reliable old and new group membership and attribution or explicit wider fallback; the current prototype chooses whole-root fallback on hardlink uncertainty. Concurrent mutations, prior unrelated changes to the same bucket, permissions and stale frontier generations must be detected or reported, not absorbed into a purported exact delta.

## 3. Bracket a user cleanup with a temporary before/after observation

**State:** Keep no permanent per-small-directory index. For a user-selected path, take a temporary **before** subtree observation, carry its aggregate/link evidence in a bounded session, then rescan after the user acts. Report the observed local change, with timestamps and uncertainty. Temporary data may scale with subtree size and cross-boundary hardlink requirements; bound it or fail gracefully. This is particularly aligned with a cleanup workflow, and it gives useful feedback without rewriting the stored coarse baseline.

**Persisted exact update is conditional:** The pre-cleanup live observation is not automatically the old contribution in the last stored bucket: that folder or a sibling may have changed since the snapshot. Applying `after − before` to an old global baseline does not make the resulting global snapshot fully current, and cannot correctly remove an unknown old freshness extremum. A reliable snapshot of the *baseline generation*, or a complete, loss-aware change journal/invalidations plus sufficient old attribution state, could validate the needed assumptions; such machinery has its own retained-state and failure costs and must fall back on gaps, overflow, restarts or uncertainty. Without it, report a local before/after observation and leave the persisted baseline stale until a wider refresh. Threshold crossings and link ownership can similarly require a wider reconciliation. This design does not claim to provide a cheap general-purpose snapshot refresh.

## Recommendation for a cleanup-focused product

Start by evaluating **option 1** as the simplest honest interaction: show coarse accumulated hotspots, then scan the specific live subtree the person chooses. It avoids permanent identities for all small objects and avoids pretending that a local observation updates an old global snapshot. It still changes the product contract and is not a universal improvement across RAM, disk, full-scan time and refresh time.

If users need repeated fast, exact persisted refreshes of a small set of known cleanup targets, evaluate **option 2** with a small, configurable frontier and visible fallback. Its hit rate, real storage and update costs are unmeasured, and no cap can remove the worst-case root rescan while preserving exact arbitrary-folder updates without equivalent historical information. **Option 3** is a useful adjunct for measuring an actual cleanup, but is not a substitute for exact snapshot refresh. None of these is an approved product contract or a claim that the current prototype implements the proposed alternatives.
